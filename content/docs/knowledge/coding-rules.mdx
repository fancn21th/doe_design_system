这页只记录 Domain UI 的实现与业务表达规则；它不定义 DOE 产品视觉语言。视觉、token、layout 或 component-composition 决策一律从 `DESIGN.md` 开始。

## Sources

- `AGENTS.md`：仓库级执行规则。
- `CONTEXT.md`：Domain UI 的术语、边界和执行协议。
- `DESIGN.md`：唯一的 DOE 产品设计系统入口。
- `docs/adr/`：架构决策记录。
- `docs/upstream/components/`：业务组件切分的上游证据。

## Domain UI Rules

1. 领域组件必须来自已确认的业务切分；不要恢复页面级组件或旧的全局状态模型。
2. 领域组件放在 `src/components/domain`，只通过稳定的 public API export。
3. 组件文档放在 `content/docs/domain/<category>`；文档至少保留 `Preview` 和 `Contract`。复杂组件按需补充 shadcn components、schema 和 scenarios。
4. Schema 是运行时入参契约。接入真实或 prototype-backed fixture 时，同步补齐 schema。
5. 基础 UI 由 `src/components/ui` 的 shadcn primitives 实现。不要自建泛用 Button、Input、Select、Dialog、Table、Tabs、Badge、Switch、Tooltip、Card 或 Dropdown Menu 替代体系。
6. 领域组件只能拥有确认过的局部展示状态和 local callback；请求、跨组件联动、数据集变更和后端状态属于应用侧。
7. 领域组件不得直接调用 `fetch`、App Service、Gateway、Oracle/MES API 或真实提交函数。`RunCard` 可以暴露回调，但不在内部执行 MES 下发。
8. `LayoutShell` 可以有本地筛选和选中状态，但不能决定应用路由。
9. 过滤器的归属必须在组件 contract 中明确：纯本地展示筛选可以内置；会改变注入数据、跨 tab 联动或触发查询的筛选属于外部状态。

## Business Expression Rules

- 不要把 `NO_DATA`、`N/A` 或 missing value 转成 `0`。
- Planned Condition 不能展示成 Actual Condition。
- 描述性证据不能展示成因果结论。
- Observed Wafer Scope 不能默认解释为 planned、released、executed 或 completed。
- Candidate Step Mapping 不能展示成已确认的 DOE Step mapping。
- Mock、derived、deterministic-template、source-provisional、prototype-backed 数据必须显式标记，不能伪装成 production fact。
- Coverage Unknown 不能展示成 pass、no issue 或 defect-free。
